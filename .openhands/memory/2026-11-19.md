## Versions chosen (and why)
- Kotlin **2.2.0** — first KGP whose Gradle plugin officially supports **AGP 8.7.3**
  (2.1.20/2.1.21 stop at 8.7.2). Gradle 8.12 is inside KGP 2.2.0's range too.
- Compose compiler: **not a dependency** from Kotlin 2.0 on. It ships as the
  `org.jetbrains.kotlin.plugin.compose` Gradle plugin and must equal the Kotlin version.
  `composeOptions.kotlinCompilerExtensionVersion` no longer exists.
- Compose BOM **2025.06.01** → material3 **1.3.2**, ui/foundation/runtime **1.8.3**.
- `androidx.activity:activity-compose:1.10.1` (pulls activity 1.10.1).
- AGP 8.7.3 / Gradle 8.12 / compile+target 35 / min 28 / NDK 27.2.12479018 untouched.

## Two CI invariants that Compose silently breaks (both fixed, not relaxed)
- **Permission count.** `ci-android-app.yml` asserts `grep -c 'uses-permission'` on the
  *merged* manifest is **<= 2**. `androidx.core:core:1.13.1` (pulled by Compose) declares
  BOTH `<permission>` and `<uses-permission>` for
  `${applicationId}.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. Removed both with
  `tools:node="remove"` markers in the main manifest. Safe because `${applicationId}` is
  resolved before merging (`ManifestHelper.setInjectableValues` → `setOverride(PACKAGE)`),
  so names match; and nothing registers a not-exported runtime receiver, which is the only
  caller of `ContextCompat.registerReceiver`'s guarded path.
- **APK lib set.** Same workflow fails on any `lib/` entry other than
  `lib/arm64-v8a/{libmain,libc++_shared}.so`. `androidx.graphics:graphics-path:1.0.1`
  (runtime dep of ui-graphics 1.8.3) ships `jni/*/libandroidx.graphics.path.so`.
  Excluded via `packaging { jniLibs { excludes.add '**/libandroidx.graphics.path.so' } }`
  (`JniLibsPackaging.getExcludes()` returns a mutable `Set<String>`, verified with javap).
  Only reached by Compose's `Path.iterator()`; this app iterates no Path.
- Also re-verified: no dependency AAR carries `assets/` (CI asserts none) and
  `ui-tooling` 1.8.3 has no assets/jni/permissions. App has no `src/*/assets` dir.

## Kotlin<->Java semantics verified empirically (kotlinc 2.2.0 + javac 17)
- An exhaustive `when` over a **Java** enum needs **no `else`** (Kotlin 2.x; adding one is
  only a "redundant else" warning). So `when (report.result)` over the 4 `Result` constants
  compiles without `else`.
- **Package-private Java constructors are callable from Kotlin in the same package**
  (`CompatibilityEvaluator.Check(...)` has a package-private ctor and works from
  `CompatibilityPresentationTest`, which lives in the same package).

## Integration shape
`SetupActivity`/`CompatibilityActivity` now `extends ComponentActivity` and hand their content
to Compose; ALL backend logic (picker, SAF grant, staging thread, `GameFolderStore`,
`GameFolderValidator`, launch) stayed in Java and was only re-expressed as state + `publish()`.
`LauncherHost.Callbacks` is the seam. Screens are stateless; `CompatibilityPresentation`
holds the display rules so they are host-testable.

## Contrast audit of the palette (found and fixed, commit b6a5717)
Body text was fine everywhere (6.4:1–15.2:1), but the **verdict marks** were not: they used one
shared set of tones for both schemes and every one failed the 4.5:1 minimum for normal text
(green tick 1.48:1 on the dark surface, amber "?" 1.31:1 on the light one). No single tone can
clear both a near-black and a near-white surface, so the verdict palette became a per-scheme
`VerdictColors` provided by `LocalVerdictColors` from `ZeroHourTheme`. Lowest value is now
5.56:1; the banner's body text stays ≥9.3:1 over the 16% tint. Re-ran CI (44627851527): green.
Lesson: a `darkColorScheme`/`lightColorScheme` pair is *not* automatically accessible — compute
the ratios for every semantic colour you add outside the M3 roles.

## Verified Compose/material3 API details by reading the AARs (no build needed)
- material3 **1.3.2** has the `LinearProgressIndicator(progress = { … })` lambda overload and
  the indeterminate `LinearProgressIndicator(modifier)` overload. Both are used.
- material3's `releaseApiElements` exposes `foundation`, `foundation-layout`, `ui`, `ui-text`,
  `runtime`, `material-ripple`, `material-icons-core` as **api** deps, so importing
  `androidx.compose.foundation.*` (`verticalScroll`, `isSystemInDarkTheme`, `Column`) without
  declaring `implementation 'androidx.compose.foundation:foundation'` is correct, not luck.
- KGP 2.2.0 `AgpCompatibilityCheck.minimalSupportedAgpVersion = 7.3.1` and there is **no upper
  bound** (the only "maxTested" logic in KGP is for Xcode), so AGP 8.7.3 is accepted.
- `kotlin { compilerOptions { jvmTarget.set(JvmTarget.JVM_17) } }` is the right DSL:
  `KotlinJvmCompilerOptions.getJvmTarget()` is a `Property<JvmTarget>`, so a String assignment
  would be wrong.

### Gotchas hit this phase
1. **Duplicate `AppTheme`** — see MEMORY.md. aapt2 only.
2. **`StatusChip` was required but unused.** Its own KDoc described exactly the compatibility
   result-row case, so `ResultRowItem` now stacks a `StatusChip` above the text instead of a
   bare `StatusIcon` + text row. Side benefit: the result is stated in *words*, not only a
   glyph, and a stacked layout survives a 200% font scale where a trailing badge would squeeze
   the text. Removing the icon dropped `Row`/`Alignment`/`size` imports.
3. **`Spacing` KDoc drifted from its values** (`screenVertical` doc said 32dp, value 28dp;
   `touchTarget` doc said 56dp, value 48dp). 48dp is the Material minimum, so the value was
   right and the doc was wrong.
4. **`AppearanceMode` KDoc named a test class that does not exist** (`AppearanceModeTest`;
   the real one is `AppearanceAndToneTest`).
5. **Contrast tests only covered scheme *role* pairs, not the pairs components compose.** A
   component draws one role on a surface defined separately (`primary` on `surfaceContainerLow`
   for headings, `error` on `surfaceContainerHigh` for the dialog title) — each half can be
   fine while the pair is not. Added `componentCompositionsClearWcagAa`. All pass, lowest is
   the light error-dialog title at 5.63:1.
6. `StatusIcon` remains used by both `StatusCard` and `StatusChip`, so it is not dead code.

defined-vs-used cross-check, color-role completeness, duplicate-resource scan per qualifier,
and a re-implementation of the WCAG maths to re-check every asserted pair before CI.

## Phase 3 — launcher screen rewrite (branch `agent/material3-ui-redesign`, CI green @ `c1e6a45`, run 44683742145)

### What changed
`LauncherStatus` (new, pure Kotlin enum, 7 constants) names the real installation states:
`NO_FOLDER`, `STAGING`, `READY`, `PERMISSION_LOST`, `INCOMPLETE`, `INVALID`, `STAGING_FAILED`,
plus `needsFolder`. `SetupActivity` sets it from the verdict it already computed — no backend
call added or moved. `LauncherUiState` gained `status`/`headline`/`detail`/`folderName`/
`enginePath`/byte counters and owns the presentation rules (`tone`, `progressFraction`,
`progressBytes`, `formatBytes`). `LauncherHost.render` now takes all ten values positionally
from Java. New components: `ApplicationHeader`, `InstallationCard`, `ConfirmDialog` (two-action,
destructive label `error`-tinted, deliberately distinct from single-action `ErrorDialog`).
Screen is `Scaffold` → `Box(TopCenter)` → one `widthIn(max=560.dp)` scrolling `Column`.

### Two real reporting bugs fixed (not cosmetic)
1. A failed copy used to fall through to `refreshStatus()`, whose verdict after a partial copy
   is "incomplete folder" — i.e. it blamed the player's folder for a copy that did not finish.
   Now `publishStagingFailed()` publishes `STAGING_FAILED` with the real failure text first, and
   the staged copy is kept so re-picking resumes incrementally.
2. `NO_ZERO_HOUR` and a genuinely incomplete folder were reported as one state. They are
   `INVALID` vs `INCOMPLETE` now, because the fixes differ (pick another folder vs add the base
   game).

### Gotchas worth remembering
- **`outlineVariant` is a decorative hairline, ~1.6–1.7:1 here.** It fails the 3:1 non-text
  minimum. `outline` is the role for a *meaningful* boundary (4.8–4.9:1 on
  `surfaceContainerLow`). I first wrote a divider contrast test asserting `outlineVariant` and it
  failed my own check — the right fix was to change the component to `outline`, not to lower the
  bar. A divider that separates two different kinds of statement is a boundary, not decoration.
- **`GameFolderStore.sourceName()` can return null** for a stale preference. The screen reads a
  null name as "no folder chosen", so a remembered folder would silently render as unchosen.
  `SetupActivity.displayNameOf(tree)` falls back to `tree.getLastPathSegment()` — the same
  fallback `GameFolderStore.remember` already applies, so both agree — and `InstallationCard`
  treats blank as unchosen via `isNullOrBlank()`.
- **`AppearanceMode.DEFAULT` exists** as a companion `val = SYSTEM`; the enum *entries* are only
  `SYSTEM`/`LIGHT`/`DARK`. `Theme.kt` already defaults to `DEFAULT`, so the screen does too.
- **No edge-to-edge in this app** (`enableEdgeToEdge`/`setDecorFitsSystemWindows` appear
  nowhere), so dropping the top app bar does not require manual inset padding; `Scaffold`'s
  `innerPadding` is enough.
- **`PrimaryActionButton(enabled=…, busy=…)`** intersects them (`enabled && !busy`), so passing
  both is redundant — and a spinner labelled "Choose game folder" would misname the running
  operation (it is the copy, not the picker). Left it disabled; the progress bar is the busy
  signal.
- **Java/Kotlin Javadoc links:** `[LauncherStatus]` is Kotlin KDoc syntax and does nothing in
  Javadoc; use `{@link LauncherStatus}`.

### Verification method (no local toolchain — CI only)
Static Python passes over the sources: unused-import scan (excluding `getValue`/`setValue`
delegates), string defined-vs-used, per-file brace/paren balance with strings+comments stripped,
cross-package type use without import, and a re-implementation of the WCAG maths to pre-check

Then two CI runs: the first failed only on `compileDebugUnitTestKotlin` — a stray extra `}` at

`ci-android-app.yml` must be dispatched by hand (`gh workflow run … --ref <branch>`) — its push

## Phase 4 — CompatibilityActivity redesign (commit `3a981a0`, fix `bd0e9d4`-ish, CI green 44687651846)

**Design decision that drove the whole phase: five words, not two.** The old screen mapped
`satisfied → "Success"` and *everything else* (failed, unverified, unreported) → `"Warning"`. That is
a false statement about Vulkan features: no build of this app can read them, on any device, so
"warning" implies a retry or another device might change the answer. New `CompatibilityPresentation
.Evidence`: `VERIFIED`, `UNSUPPORTED`, `UNABLE_TO_VERIFY`, `NOT_REPORTED`, `NOT_AVAILABLE`. The three
unknowns are deliberately distinct and there is a test asserting they stay 3 distinct values.
Tone map: SUCCESS / DANGER / WARNING / NEUTRAL / NEUTRAL — only verified and unsupported get an
assertive colour, so a missing fact is never drawn like a passing one.

**Structure:** `CompatibilityScreen.kt` = 5 sections (summary card → checks list → app requirements →
device info → "Not verified"). Checks were *inside* the summary card before; pulling them out keeps
the verdict on the first screenful. `CompatibilityResultCard.kt` → renamed `CompatibilityCards.kt`
holding `CompatibilitySummaryCard` + `CompatibilityCheckList` + `CheckRow` data class.

**Back navigation was never wired at all** — `onNavigateBack` defaulted to null so `ApplicationTopBar`
drew no arrow. Now `CompatibilityActivity` passes
`() -> getOnBackPressedDispatcher().onBackPressed()` (not the deprecated `Activity.onBackPressed()`).

**Kotlin↔Java gotcha that broke CI:** a Kotlin parameter typed `(() -> Unit)?` is **not** assignable
from a Java `void` lambda — `error: incompatible types: bad return type in lambda expression / void
cannot be converted to Unit`. `CompatibilityActivity.java` passing `() -> ...onBackPressed()` failed.
Fix: type the host parameter `Runnable?` (Java-facing shape) and adapt once at the Compose boundary
(`onNavigateBack?.let { r -> { r.run() } }`). Use `Runnable` for any Java-called single callback in
the `@JvmName` host objects; `LauncherHost` avoids this by taking a multi-method Java interface.

**Contrast:** summary card border uses `outline` (5.78:1 dark / 5.27:1 light) not `outlineVariant`
(1.71/1.62) because it bounds the verdict; check-row dividers stay `outlineVariant` and are
documented as *decorative* (chips already separate rows) so they legitimately carry no 3:1 duty.
Added `compatibilitySummaryOutlineIsVisible` to `WcagContrastTest` after computing the ratios in
Python from `BrandPalette.kt` first — always compute before asserting, don't guess a threshold.

**String hygiene:** the redesign orphaned `compat_value_graphics`, `compat_value_android_version`,
`compat_value_unknown`, `compat_vulkan_hardware_level`, `compat_vulkan_unverified_note` — deleted
rather than left dead. Vulkan requirement split into 3 rows (floor / required extensions / required
features) because a reader compares an extension list against a driver report.

**Tooling quirk (cost me real time):** large `cat >> file <<'KOTLIN'` heredocs in this terminal
**silently fail to write** — the command reports exit 0 and echoes the text, but the file keeps its
old content (and once injected stray Cyrillic chars into an import line). For anything over ~100
lines use `file_editor insert`/`create`, or write with a Python script; always re-read the file
afterwards (`wc -l`, `grep -c`) instead of trusting exit code 0. `/tmp/hdr.txt` also disappears
between sessions — recreate it from `sed -n 1,18p` of any existing source file.

**Result:** 74 → 82 host tests (CompatibilityPresentationTest 5→10, WcagContrastTest 11→12), all
green; merged-manifest and ELF audits unaffected. No Java compatibility logic touched.
